# Jarvis for iOS

A native iOS shell around [Jarvis](../docs/jarvis.html), built with
[Capacitor](https://capacitorjs.com). Capacitor wraps the same self-contained
web app in a real iOS app (`WKWebView` + native plugins), which is what makes
it distributable through the App Store instead of just "Add to Home Screen."

Everything up through a buildable, signable Xcode project is done. What's
left needs a Mac, Xcode, and your own Apple Developer account — I can't do
those parts from here.

## Why this isn't just a copy of `docs/jarvis.html`

`www/index.html` is a fork of the web app with one real difference: **voice
input**. iOS's WKWebView has never implemented the Web Speech API
(`SpeechRecognition`), so the browser-only version would be silently reduced
to text input on iOS. This fork adds a small engine-selection layer at the
top of the speech-recognition code — when it detects it's running natively
(`Capacitor.isNativePlatform()`), it drives the on-device
`@capacitor-community/speech-recognition` plugin (Apple's `SFSpeechRecognizer`)
instead of the missing browser API. Everything else — the UI, the tools,
memory, smart home, multi-model teamwork — is identical to the web app.

Two smaller upgrades come along for free in the native build:

- **Reminders fire even if the app is closed.** The web version can only
  remind you while the tab is open (`setTimeout`); the native build also
  schedules a real OS notification via `@capacitor/local-notifications`.
- **Weather location and Home Assistant** now go through iOS's own location
  and local-network permission prompts instead of the browser's.

If you change something in `docs/jarvis.html`, the equivalent change needs
porting into `mobile-app/www/index.html` by hand — they're intentionally
separate files rather than one build pipeline, so a change to one can't
silently break the other.

## What's already done

- `capacitor.config.json` — app id `com.henrythebozo.jarvis`, app name
  "Jarvis", dark background.
- `ios/` — a full Xcode project (`App.xcworkspace`), generated by
  `npx cap add ios`.
- App icon and launch screen — a small cyan orb on black, matching the
  in-app HUD (see `assets/icon-only.png` / `assets/splash.png`). The source
  is upscaled from a 512×512 PNG; swap in a real 1024×1024 (or larger)
  version and rerun `npx capacitor-assets generate --ios` before shipping if
  you want it crisp.
- `Info.plist` — usage-description strings for microphone, speech
  recognition, location (weather), and local network (Home Assistant), plus
  an App Transport Security exception (see note below).
- Local notifications + on-device speech recognition wired into the app code.

## What I could not do (no Mac in this environment)

- Run `pod install` — CocoaPods needs to run on macOS. **You'll need to run
  this yourself before the project will open cleanly.**
- Open, build, or run the project in Xcode.
- Test the native voice/notification code on a real device or simulator —
  I've implemented it to match the plugins' documented behavior, but it
  hasn't run on an actual iPhone yet. Treat the voice flow especially as
  something to test and tune first (see below).
- Anything requiring your Apple Developer account: signing, registering the
  bundle ID, App Store Connect, submission.

## Setup (on your Mac)

```bash
# 1. Install CocoaPods if you don't have it
sudo gem install cocoapods   # or: brew install cocoapods

# 2. From mobile-app/
npm install
npx cap sync ios
cd ios/App && pod install && cd ../..

# 3. Open the WORKSPACE (not the .xcodeproj — Pods only load via the workspace)
open ios/App/App.xcworkspace
```

## In Xcode

1. Select the **App** target → **Signing & Capabilities** → set your **Team**.
   A free Apple ID lets you run on your own device for 7 days at a time; you
   need a paid **Apple Developer Program** membership ($99/yr) to submit to
   the App Store.
2. If `com.henrythebozo.jarvis` isn't available to your account, change the
   **Bundle Identifier** to one under a domain/name you control — do this
   before your first archive, since it's part of the App Store listing.
3. Plug in an iPhone (or pick a Simulator) and hit **Run**. Check, in order:
   - Settings opens on first launch and saves an API key.
   - Push-to-talk mic: tap, speak a question, confirm it transcribes and
     Jarvis answers out loud.
   - Wake-word mode, if you use it.
   - The record button: speak for a bit, stop, confirm a transcript saved
     under Recordings, and "Analyze" produces a summary.
   - Settings → set a reminder for 1 minute, background the app, confirm a
     real notification arrives.
   - Home panel devices toggle; if you have Home Assistant, test that too.
4. **Tune if needed**: the native voice engine ends a spoken command after
   ~1.4s of silence (`nativeSilenceTimer` in `www/index.html`) — adjust that
   number if it cuts you off or waits too long. This is the one piece of
   behavior I'd most expect to need a real-device pass.

## Shipping

1. **Product → Archive** (destination must be "Any iOS Device", not a
   Simulator).
2. In the Organizer that opens, **Distribute App → App Store Connect →
   Upload**.
3. In [App Store Connect](https://appstoreconnect.apple.com), create a new
   app with the same bundle ID, then fill in:
   - **Screenshots** (required sizes per device family you support).
   - **Privacy Policy URL** — required, and worth getting right: this app
     itself collects nothing and runs no server. Chat content, audio, and
     API keys go straight from the device to whichever AI provider the user
     configured, using a key *they* supplied — not through anything of
     ours. Say that plainly, and disclose the specific third parties data
     can reach based on what a user configures (OpenAI, Anthropic,
     OpenRouter, Open-Meteo, and optionally the user's own Home Assistant
     server).
   - **App Privacy questionnaire** — answer based on the above: no data
     collected *by the developer*; data a user's own configured AI
     provider receives is on them, not this app.
4. Submit for review.

### One thing Apple review may ask about

`Info.plist` sets `NSAllowsArbitraryLoads: true`. This is because the AI
provider and Home Assistant URLs are entered by the user in Settings, so the
exact hosts aren't known in advance, and a self-hosted Home Assistant
instance is often plain HTTP on the local network. If review flags it,
explain exactly that in the review notes. If you'd rather tighten it, the fix
is scoping `NSExceptionDomains` per-host instead — not practical here since
Home Assistant's host is user-defined, but doable if you want to lock down
the AI-provider domains (which are fixed) and leave only local networking open.
